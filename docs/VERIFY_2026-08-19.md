# ⏰ Verify on 2026-08-19 — email sends + retainer

Two systems went from "code deployed" to "actually running in live mode" on
2026-08-18 and **neither has been observed working yet**. Both fail *silently* —
nothing errors, nothing alerts, the dashboard just quietly shows the wrong
thing. That is exactly why they need a deliberate check rather than an
assumption.

---

## 1. Did the reminder emails actually send?

**Background.** 354 reminders were armed for the 185 imported FareHarbor
bookings (176 × 24h, 178 × 2h). First send was **2026-08-18 16:00 UTC**
(11:00 America/Chicago). Before this, the email path had **never** run in
production for real customers.

**The specific risk.** `emailConfigured()` (`bookingsystem/src/lib/email/client.ts:13`)
returns false unless BOTH `RESEND_API_KEY` and `EMAIL_FROM_ADDRESS` are set, and
when it returns false every send is `{ status: "skipped", reason: "not_configured" }`
— *silently*. Both vars exist in the bookingsystem Vercel project but are marked
**Sensitive**, so their values could not be read to confirm correctness. A wrong
or unverified from-domain fails the same quiet way.

### Check (run in `~/turbobookings-dashboard`)

```
npm run emails:status -- dtown
```

**Reading the result:**

| Signal | Meaning |
|---|---|
| `sent` climbing, `sent_at` populated | ✅ working |
| `pending` only, nothing sent, `attempt_count = 0` | 🔴 **cron not firing** — check the Vercel cron for `/api/cron/scheduled-emails` and `CRON_SECRET` |
| `attempt_count > 0` with `last_error` | 🔴 read the error; likely Resend auth or unverified domain |
| Rows silently stuck, no error, no send | 🔴 almost certainly `emailConfigured()` false — verify `RESEND_API_KEY` + `EMAIL_FROM_ADDRESS` in the **bookingsystem** project |

Also confirm in the **Resend dashboard**: sends are landing, the domain is
verified, and bounce/complaint rates are sane. These 185 people booked through
FareHarbor and have never received mail from this sender, so a bad from-domain
would burn reputation on the very first batch.

**If it is broken:** the emails are not lost. Rows stay `pending` and the cron
retries with backoff (6 attempts). Fix the config and they drain on their own.
Do NOT re-run the backfill — the idempotency keys make it a no-op anyway, but
the failure is upstream of scheduling.

## 2. Does the retainer track status correctly in live mode?

**Background.** Dallas held **test-mode** `stripe_subscription_id` /
`stripe_platform_customer_id`. Because the dashboard webhook updates by matching
that ID (`api/webhooks/stripe` → `setStatusBySubscription`), live events could
never match, so `retainer_status` was frozen at `active` — showing a healthy
paying client for a subscription billing nobody. Cleared 2026-08-18; Dallas now
correctly reads `inactive`.

**This is not fixed yet — it is only unblocked.** The repair happens when
Richard adds the live card and Start retainer is pressed, because
`startSubscription()` is what writes the live `sub_…` back to the row.

### Order matters — and the guard will NOT protect you
1. **Card first, saved to completion.**
2. **Then Start retainer.**

⚠️ As of 2026-08-18 05:16 UTC a **live** platform customer already exists
(`cus_V5r1dSDT62TpoJ`) but **no card is saved** — the billing form was opened
(`ensurePlatformCustomer` runs when the SetupIntent is created) and not finished.

`startSubscription()` guards on the **customer id, not the card**:

```ts
if (!location.stripePlatformCustomerId) throw new Error("No card on file");
```

So pressing Start now would pass that check, create a subscription with no
payment method, sit in `trialing` (which `mapSubStatus` maps to **active**), and
only fail on billing day 15 — a delayed false-active. The card is genuinely saved
only when `retainer_card_last4` is populated. `npm run retainer:status -- dtown`
flags this state explicitly.

### Check (run in `~/turbobookings-dashboard`)

```
npm run retainer:status -- dtown
```

Expect: `sub` = a **live** `sub_…`, `cust` = a live `cus_…`, `status` = `active`,
amount 325000, day 15.

### Then prove the failure path actually reports

Status showing `active` only proves the happy path. The bug being fixed here was
a **false active**, so verify the *failure* direction:

- In the Stripe **live** dashboard, open the subscription and check that the
  event destination `dashboard-retainer-subscriptions`
  (`we_1U5eUFE69fk80FRq1tlWeB7f`) shows **successful deliveries** for
  `customer.subscription.created`.
- 0 deliveries ⇒ the webhook is not wired to this subscription and a future
  failed payment will still show `active`.

**Watch for:** `invoice.payment_failed` is deliberately NOT subscribed. Stripe
sets `subscription.status = past_due` on a failed invoice, which fires
`customer.subscription.updated` — that is the event doing the work. If status
ever stops tracking, check that this event is still subscribed before anything
else.

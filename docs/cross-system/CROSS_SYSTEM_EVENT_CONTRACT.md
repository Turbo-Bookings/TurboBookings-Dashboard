# Cross-System Event Contract

**Status:** Canonical for the ENVELOPE and transport. The event catalog in §4 is partly aspirational —
see the reality check below.
**Purpose:** Single source of truth for events flowing Vercel → the brains.

> ## ⚠️ Reality check (2026-08-21) — read before building against §4
>
> This document was written when the receiver was going to be the Replit app. **That receiver was never
> built** — `source_surface` / `occurred_at` appear nowhere in `~/takeovers-platform`. The live receiver
> is the **ad cockpit** on Railway; see **`BOOKING_TO_COCKPIT_FEED.md`** for what actually runs.
>
> Corrections to this document, verified against the code:
>
> | §4 says | Reality |
> |---|---|
> | 13 event types | **Six** are emitted: `booking.created`, `.cancelled`, `.checked_in`, `.no_show`, `.rescheduled`, `communication.requested`. The other 13 (`page.viewed`, `ad.click_landed`, `payment.succeeded`, `checkout.*`, `customer.*`, `dashboard.*`) have **zero call sites** |
> | `booking.checked_in` / `.no_show` / `communication.requested` | Live, and absent from §4 entirely |
> | Retry `1s, 5s, 30s, 5min, 30min, 6h` | Code uses **`1m, 5m, 30m, 6h, 6h, 6h`**, `MAX_ATTEMPTS = 6` |
> | Secret in `location_secrets` | Read from `process.env` (`BRAIN_WEBHOOK_SECRET ?? REPLIT_WEBHOOK_SECRET`) |
> | `tour_key`, `customer_type`, flat `email_lower` | Emitted as `tour_id`, `customer_type_id`, nested `data.customer{…}` |
> | Dead letters queryable from the dashboard | Not built. Query `succeeded_at IS NULL AND attempt_count >= 6` |
> | `last_attribution_click_id` / `_type` spec'd but never sent | **Now real** (2026-08-28). Both bases ship on `booking.created`; the cockpit stores them as `ref` (last) and `ref_first` (first) |
>
> **`booking.created` has TWO shapes.** `source_surface: "booking_system"` sends the full payload;
> `"dashboard"` (operator/manual bookings) once sent only `{booking_id, source}`. Fixed 2026-08-21 —
> both now send the same payload via `buildBookingCreatedPayload()`. A receiver should still tolerate
> the thin shape for replayed history.
>
> **`REPLIT_WEBHOOK_*` is a fossil — nothing is ever sent FROM Replit.** It is the key our storefront
> signs outbound events with. `BRAIN_WEBHOOK_*` is preferred; the legacy names remain as a fallback.
>
> **Receivers MUST key off `occurred_at`, not receipt time.** The queue drains oldest-first and held
> events two months old.

## 1. Direction and transport

**Direction:** Vercel → brains only. The brains never write back to the Vercel database.

**Transport:** HTTPS POST. Live endpoint: `https://cockpit.turbobookings.net/api/webhooks/turbobookings` (see BOOKING_TO_COCKPIT_FEED.md).

**Auth:** HMAC-SHA256 signature in the `X-Turbobookings-Signature` header, computed over the raw request body using a shared secret. Replit verifies signature before processing.

```
X-Turbobookings-Signature: sha256=<hex digest>
X-Turbobookings-Tenant: <tenant_uuid>
X-Turbobookings-Event-Id: <uuid v4, generated by sender>
Content-Type: application/json
```

**Secret rotation:** Per-tenant secret stored on Vercel side in `location_secrets` table under key `REPLIT_WEBHOOK_SECRET`. Replit holds the same secret keyed by tenant.

**Retry:** Sender retries on non-2xx response with exponential backoff: 1s, 5s, 30s, 5min, 30min, 6h. After 6 failed attempts the event lands in a Vercel-side dead-letter table for manual review.

**Idempotency:** Replit deduplicates on `event_id`. Resending the same `event_id` is a no-op (returns 200 OK). This makes retries safe.

## 2. Envelope

Every event uses this envelope:

```json
{
  "event_id": "uuid-v4",
  "event_type": "namespace.action",
  "event_version": "1.0",
  "occurred_at": "2026-05-26T14:32:17.482Z",
  "tenant_id": "uuid",
  "location_id": "uuid",
  "source_surface": "marketing_site" | "booking_system" | "dashboard",
  "data": { /* event-specific payload */ }
}
```

**Field rules:**
- `event_id` — UUID v4, generated by the sender at emit time. Used for dedup.
- `event_type` — namespaced dot-notation, lowercase. See full list in §4.
- `event_version` — semver. Bump major when payload shape changes incompatibly.
- `occurred_at` — ISO 8601 with milliseconds and Z suffix. The time the event actually happened, not the time it was sent.
- `tenant_id` — the agency/parent tenant UUID. For Turbobookings's own three locations, this is the Turbobookings tenant UUID.
- `location_id` — the specific location the event belongs to.
- `source_surface` — which Vercel surface emitted it.
- `data` — per-event-type payload, schema below.

## 3. Identity model

Every event MUST carry at least one identity. Listed in priority order:

| Identity | Field | When to send |
|---|---|---|
| Customer ID | `data.customer_id` | When the event happens to a known customer record (post-booking, post-signup) |
| Anonymous ID | `data.anonymous_id` | Pre-identification browsing on the marketing site |
| Email | `data.email_lower` | When captured but customer record not yet created |
| Phone (E.164) | `data.phone_e164` | When captured but customer record not yet created |

**Multiple identities are allowed and encouraged** — send everything you have. Replit's identity resolution layer merges based on whatever it can match.

**`anonymous_id` rules:**
- 36-char UUID v4, lowercase
- Generated on first visit to a marketing site, stored in a first-party cookie (`tb_aid`) with `Max-Age=63072000` (2 years)
- Persists across pages on the same site
- Forwarded as a query param when the customer navigates into the booking system (e.g., `/book/atv-1h?tb_aid=...`)
- Stored on the booking system side in session storage during the booking flow
- Sent in every event from any Vercel surface for that session

## 4. Event catalog

### 4.1 Marketing site events

#### `page.viewed`

Fires on every page load.

```json
{
  "event_type": "page.viewed",
  "data": {
    "anonymous_id": "uuid",
    "customer_id": "uuid|null",
    "url": "https://htownatvrentals.org/tours/atv-1h",
    "path": "/tours/atv-1h",
    "referrer": "https://google.com/...",
    "utm_source": "google",
    "utm_medium": "cpc",
    "utm_campaign": "htown_atv_summer",
    "utm_content": "ad-id-12345",
    "utm_term": null,
    "gclid": "EAIaIQ...",
    "fbclid": null,
    "wbraid": null,
    "gbraid": null,
    "user_agent": "...",
    "ip_address": "1.2.3.4",
    "viewport_w": 1440,
    "viewport_h": 900
  }
}
```

**Throttling rule:** Don't send more than one `page.viewed` per anonymous_id per URL per 30 seconds. Pure SPA navigation between the same canonical URL doesn't fire a new event.

#### `ad.click_landed`

Fires when a page load detects a click ID in the URL. Separate from `page.viewed` because this is a higher-value signal that should never be throttled or dropped.

```json
{
  "event_type": "ad.click_landed",
  "data": {
    "anonymous_id": "uuid",
    "platform": "meta" | "google" | "tiktok" | "bing",
    "click_id": "EAIaIQ...",
    "click_id_type": "gclid" | "fbclid" | "wbraid" | "gbraid" | "ttclid",
    "landing_url": "https://htownatvrentals.org/tours/atv-1h",
    "utm_source": "facebook",
    "utm_medium": "paid_social",
    "utm_campaign": "htown_summer_2026",
    "utm_content": "creative_id_98765"
  }
}
```

#### `email.subscribed`

Fires when a customer submits an email-only signup (popup, footer, etc.).

```json
{
  "event_type": "email.subscribed",
  "data": {
    "anonymous_id": "uuid",
    "email_lower": "jane@example.com",
    "source": "homepage_popup" | "footer_form" | "tour_page_popup" | "exit_intent",
    "consent_text_shown": "Yes, send me deals and trip ideas.",
    "ip_address": "1.2.3.4",
    "user_agent": "..."
  }
}
```

**TCPA/CAN-SPAM compliance:** `consent_text_shown` is the literal text the customer agreed to. Store it verbatim — this is your audit trail if a regulator asks.

#### `sms.subscribed`

Fires when a customer submits a phone number for SMS opt-in. Separate event from `email.subscribed` because TCPA requires affirmative opt-in for SMS specifically.

```json
{
  "event_type": "sms.subscribed",
  "data": {
    "anonymous_id": "uuid",
    "phone_e164": "+13055551234",
    "email_lower": "jane@example.com|null",
    "source": "homepage_popup" | "tour_page_form",
    "consent_text_shown": "I agree to receive SMS messages from H-Town ATV Rentals. Msg & data rates may apply. Reply STOP to unsubscribe.",
    "ip_address": "1.2.3.4"
  }
}
```

#### `booking.created`

Fires when a payment succeeds and a `bookings` row is finalized.

```json
{
  "event_type": "booking.created",
  "data": {
    "booking_id": "uuid",
    "customer_id": "uuid",
    "anonymous_id": "uuid|null",
    "tour_key": "atv1h",
    "tour_display_name": "1-Hour ATV Tour",
    "scheduled_at": "2026-06-15T14:00:00.000Z",
    "party_size": 4,
    "booking_lines": [
      {
        "customer_type": "adult",
        "quantity": 2,
        "unit_price": 8900
      },
      {
        "customer_type": "child",
        "quantity": 2,
        "unit_price": 4900
      }
    ],
    "subtotal": 27600,
    "tax": 2208,
    "platform_fee": 800,
    "total": 30608,
    "currency": "USD",
    "payment_id": "uuid",
    "stripe_payment_intent_id": "pi_...",
    "source": "online_self_serve" | "phone_agent" | "operator_manual",
    "booking_source_detail": "string|null",
    "discount_code": "SUMMER10|null",
    "first_attribution_click_id": "fbclid_value|null",
    "first_attribution_click_type": "fbclid|null",
    "last_attribution_click_id": "gclid_value|null",
    "last_attribution_click_type": "gclid|null"
  }
}
```

**Attribution fields — as built, 2026-08-28.** Both bases are now sent, and they come from different
places because their cardinality differs:

| Field | Source | Scope |
|---|---|---|
| `first_attribution_click_*` | `customers`, set on INSERT only | once per **person** — discovery |
| `last_attribution_click_*` | `bookings`, set per row | once per **purchase** — conversion |

They are resolved at checkout from our own first-party `tb_click_first` / `tb_click_last` cookies,
written from the landing URL by proxy, with `_fbc` / `_gcl_aw` as a legacy fallback. The original note
here said Vercel "should compute" these from the `anonymous_id`'s touchpoint history — there is no
touchpoint history, and there is no Replit receiver to "reconstruct" anything, so that path was never
available. The cookies are what makes both bases real.

The two are frequently equal, which is meaningful rather than redundant: it says one platform did the
whole job unaided. Null means organic, direct, or a click we could not capture — never zero.

## 5. Marketing consent — special handling

Consent flows are bidirectional in concept but unidirectional in implementation. Here's how it works:

1. **Opt-in captured on Vercel** (popup, booking form, etc.) → `email.subscribed` / `sms.subscribed` / `customer.updated` event fires → Replit records original opt-in metadata in its `customer_marketing_state` table.

2. **Replit owns current consent state** — when Replit sends a marketing email or SMS, it checks its own `customer_marketing_state` table, not the Vercel `customers.marketing_*_consent_at` fields.

3. **Unsubscribes happen on Replit** (unsubscribe links go to Replit-hosted endpoints, SMS STOP messages route to Replit). Replit updates its own state. **It does not push the unsubscribe back to Vercel.**

4. **Vercel's `marketing_*_consent_at` fields are an audit record of original opt-in**, not the source of truth for current consent.

If a customer un-subscribes on Replit and then re-subscribes via a Vercel popup later, the new `email.subscribed` event tells Replit to re-enable consent.

## 6. Implementation acceptance criteria

### Vercel side
- [ ] Every event listed in §4 is emitted from the correct surface at the correct trigger point
- [ ] All events include the full required envelope (§2)
- [ ] All events carry at least one identity (§3)
- [ ] `anonymous_id` cookie is set on first marketing-site visit and forwarded through to booking system
- [ ] HMAC signature is computed and sent on every request
- [ ] Failed deliveries retry with exponential backoff per §1
- [ ] Dead-lettered events are queryable from the dashboard

### Replit side
- [ ] `/api/webhooks/inbound` accepts all event types
- [ ] HMAC signature is verified before any event is processed
- [ ] `event_id` dedup means the same event posted twice is a no-op
- [ ] Unknown `event_type` returns 200 OK (forward compatibility) but logs a warning
- [ ] Each event lands as a row in the `touchpoints` table within 1 second of receipt
- [ ] Identity resolution runs synchronously on `customer.created` and `email.subscribed` events

## 7. Versioning

When an event payload changes shape:

- **Backward-compatible additions** (new optional field): no version bump
- **Backward-incompatible changes** (rename, remove, type change): bump `event_version` major, ship both versions in parallel for 30 days, then sunset the old

Replit must support every active major version simultaneously.

---

## 8. What this contract does NOT cover

- Internal Replit events (e.g., voice agent → marketing module). Those are app-internal, not cross-system.
- Vercel → Vercel events (dashboard → booking system). Those happen via direct DB reads on the shared Neon.
- Replit → Vercel writes. Not allowed. Don't add them.
